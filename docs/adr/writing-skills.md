# 写作类 skill 的共同决定

适用于 `skills/` 下的全部 skill。各 skill 自己的决定见同目录下以 skill 名命名的文件。

## 分工与调用关系

- `write-article`：长文，从想法到成稿的协作写作。
- `write-tweet`：X 推文。
- `writing-ai-check`：只找并改掉稿件里的 AI 味，输入是一篇稿件，不依赖写作过程。
- `rewrite-en2zh`：把英文内容重写成简体中文。
- `writing-style-learn`：把作者的亲笔稿、改稿和原话写进风格档案，整理和校准档案。
- `writing-style-setup`：建风格档案，把档案路径写进项目配置。
- `wechat-publish`：预览公众号排版，把文章同步到公众号草稿箱。

每个 skill 自包含，只读自己目录下的文件，外加作者的风格档案（见下文）。AI 味特征清单只在 `writing-ai-check/SKILL.md` 一处。

写作 skill 互不调用。稿件写完后需要清理 AI 味时，由用户单独运行 `/writing-ai-check`。以后需要“先写后查”的组合流程时，单独写一个编排 skill，交接规则只写在那里。

理由：组织内容和清理表达是两件事。放在一个 skill 里，主文件同时承载协作流程和大量特征清单；清理表达对任何稿件都适用，绑在写作流程里就不能单独使用。写作 skill 调用检查时，交接要讲清体裁、排版约定、固定句式和待定项的去向，这些是编排问题，写在写作 skill 里会让它同时管写作和调度。

代价：只运行写作 skill 时，交付的稿件没经过 AI 味检查。

## 调用方式

`write-article`、`write-tweet`、`rewrite-en2zh`、`writing-style-learn`、`writing-style-setup`、`wechat-publish` 设为显式调用：`SKILL.md` 加 `disable-model-invocation: true`，`agents/openai.yaml` 设 `policy.allow_implicit_invocation: false`。

`writing-ai-check` 保持 model-invoked，`agents/openai.yaml` 设 `policy.allow_implicit_invocation: true`，留给编排 skill 按名调用。它的「被其他 skill 调用」一节写的是调用方交来的前提怎么处理。误触发靠 description 收窄：只在用户或调用方明确写出 `/writing-ai-check` 时使用。

理由：这些 skill 的触发词（写、改、翻译）在别的任务里也常出现。自动命中后，agent 会把一次顺手的编辑升级成多阶段协作，或改写用户没打算交出去的文字。user-invoked 的 skill 只响应用户在输入框里写的名字，别的 skill 调不到它。

description 仍要写清触发场景，供用户在 skill 列表里认出它们。

## 流程、写法经验、个人风格分三层

`write-article` 和 `write-tweet` 都分三层：

- 流程在 `SKILL.md`：基本约定、步骤与完成标准、每步读哪个参考文件、排版。
- 写法经验在 `references/`，按读取时机拆文件，一个文件回答一类问题。每条是启发工具，写明适用情形，不作为评分表，不计分、不凑项。
- 个人风格不在 skill 里，在作者的风格档案。

新经验进入文件前按这个顺序归类：事实底线进 `SKILL.md` 基本约定或对应步骤；特定写法的要求进对应写法的参考文件并写明适用情形；通用讲述方法进其余写法经验文件；个人偏好由 `writing-style-learn` 写进风格档案；一次性修改不进文件。只出现一次的问题先观察，反复出现再写成规则。

理由：流程随协作方式变，写法经验随实际稿件积累，个人风格只随作者本人的文字变，三者改动时机不同。拆开后改一条只动一个文件。方法写成每篇的验收门槛时，会把各种文章都推向亲身实践和经验复盘，所以写成启发工具并写明适用情形。

同一条规则写作时的说法和复查时的说法各只有一处。参考文件增减时，同步 `SKILL.md` 里的读取时机和子代理交接清单，避免出现没人读的文件。引用外部规范时给链接，不抄内容。

## 个人风格放在 skill 之外的风格档案

skill 只写通用流程和通用写法，可以发布给别人用。作者的个人风格放在一份独立的风格档案里，写作 skill 共用。

### 结构

```
writing-style/
  index.md              文件清单和使用说明
  style.md              每句话怎么说，所有体裁通用
  genres/<体裁>/
    default.md          适用、语气、结构、讲事和解释、排版、固定表达、类型列表、范文
    <类型>.md            只写和 default 不同的部分，链接范文
    examples/           范文：作者圈出的段落或整篇
  candidates.md         还没定的写法，开头带条目格式
```

- 写稿分两步：先按体裁和类型定整体结构，再按 style.md 定每句话怎么说。所以按「依不依赖位置、篇幅、分段、类型或平台」分文件：依赖类型的进类型文件，依赖体裁的进 default.md，其余进 style.md。
- 档案只放作者的写法；怎么读、怎么写规则、怎么检查写在 skill 里。例外是 index.md 的「使用说明」、每节标题下的「用法：」一行和 candidates.md 开头的格式说明：档案自己说明怎么读、怎么用、怎么往里追加，读它的一方只要知道 index.md 在哪。

理由：

- 个人风格随作者本人的文字变，和通用写法的改动时机不同。写在 skill 里，skill 不能发布。
- 长文和推文的说话方式大部分相同，共用 style.md；体裁和类型只管语气、结构、排版和固定表达。
- style.md 分作者与读者、口头习惯、标点和排版、讲事和解释、禁用词表五节，节都要建；体裁和类型文件的节可选，没有内容就不建。不设术语表：叫法规则放讲事和解释，大小写由标点和排版管，单列一组词会和这两处重复。
- 类型文件替代了 write-article 原来的 `references/genres.md`：文章分哪几类、每类怎么推进，是作者自己的习惯，通用的分类和检查清单会和它打架。代价是没有档案时，write-article 不再有分类型的缺口和检查。
- 档案也会被没装这些 skill 的 agent 读到。index.md 带一份简短的使用说明（读哪些文件、优先级、照各节的用法、语气和句子照例子学而内容不搬、候选不用于写稿），这些 agent 只读 index.md 也能照档案写。
- 范文收作者圈出的段落，也收作者整篇认可的文章。整篇里常有作者不想要的写法，只收整篇时档案里一段连续的亲笔文字都没有，模型学不到节奏和语气。default.md 也能链接范文，不属于某个类型的段落有地方放；除「适用」外写不出内容的类型不建文件，免得写稿时多选一步、多读一个空文件。
- 整篇亲笔稿由作者挑要留的段落和写法，learn 不自己提炼：从整篇里提炼出来的规则，多数不是作者想要的。

### 各部分定义在哪

| 部分 | 定义在 |
| --- | --- |
| 目录、文件名、index.md 的「使用说明」 | `writing-style-setup` 第 2、3 步 |
| 各文件的骨架和节名、每节放什么和「用法：」一行、规则格式、规则放哪、candidates.md 的格式 | `references/archive-format.md`，learn 和 setup 各一份 |
| 依据、什么时候建类型和范文、候选怎么升级、校准 | `writing-style-learn` |
| 什么时候读档案、往 candidates.md 追加什么 | `write-article`、`write-tweet` 的「风格档案」一节 |

archive-format.md 两份内容相同：skill 分开安装，只能读自己目录下的文件，setup 建档要用骨架，learn 写规则要用格式和放哪。以 learn 那份为准，改完复制到 setup，检查脚本比对两份。合成一个文件，是为了档案格式能从头读到尾，不用在两个 SKILL.md 里拼。

写稿 skill 不抄使用说明，只指向 index.md：有档案就一定有 index.md，写稿前本来就要读它。使用说明只在 setup 的模板和它生成的 index.md 两处，改动时改模板，旧档案重跑 setup 换成新版本。候选的格式同理，写在 candidates.md 开头，写稿 skill 照它追加。两个写稿 skill 的「风格档案」一节除体裁名和目录外一致，靠 `scripts/check_writing_style_sync.py` 检查。

代价：档案比 skill 旧时，写稿按旧的使用说明走，要重跑 setup 才更新。

### 读和写

- 指向：档案路径写在项目的 AGENTS.md（只有 CLAUDE.md 时写它）`## Agent skills` 下的 `### Writing style profile`。写代码的项目不写，就不受影响。公开仓库里写个人路径会随提交公开，setup 会提醒改写进 CLAUDE.local.md。
- 读：写稿 skill 读 style.md、本体裁的 default.md、选中的类型文件，以及 default.md 和类型文件链接的范文。candidates.md 不读。`writing-ai-check` 只管 AI 味，不读档案。
- 优先级：用户本次的要求和 skill 的基本约定 > 类型文件 > default.md > style.md > skill references 里的通用写法。越具体的越优先。
- 写：写稿 skill 只往 candidates.md 末尾追加作者的手改和原话；其余由 `writing-style-learn` 写。多个写入方各改规则时，同一条规则会叠出几个版本。
- 依据只能是作者本人写且认可的文字：亲笔稿、手改、原话。agent 写的段落和数据表现只作向作者提问的线索。

理由：候选不读，是因为它还没经作者确认是一贯写法，只出现一次的改法多半只针对那一篇；写进候选后要等 learn 和作者确认才生效。

### 规则

每条规则一个 `###` 标题，写这条规则管的对象或场景；下面写 1～3 句做法，可选一行「原因：」、一行「适用：」，再跟真实例子（`<改前>` 加 `<改后>`，或 `<亲笔>`，前面可以加一行「背景：」）。

- 标题就是规则名。标题只写对象，不总结做法：一句话的标题装不下做法的边界，做法写在正文里。
- 例子用标签包起来，原文的起止一眼能看出，跨几段时也不会和做法混在一起。
- 背景写为什么这么改，或读懂例子要的上下文，都没有就不写。不写出自哪篇稿子：写稿的 agent 找不到原稿，出处帮不了它判断规则在本次材料里怎么用。
- 文件位置已经交代的条件不写进标题；其余限定写进「适用」，缩窄规则时只改这一行。
- 原因只写作者说过的。必填会逼 learn 编原因，编出来的原因是泛泛描述，误导模型。
- 例子跟着规则放，可以有几组，原文照抄。规则管说什么，例子管长什么样；改一条只动一处。没有真实例子就不写，不编。

代价：标题只写对象，扫一眼标题看不出规则要求什么，要读做法。禁用词表会把这些词带进写稿的上下文。

### 各节怎么用

规则不标强度。写稿时怎么用由规则所在的节决定，写在节标题下的「用法：」一行，使用说明第 4 条只说照它用：

| 节 | 写稿时 |
| --- | --- |
| style.md 作者与读者 | 背景 |
| style.md 标点和排版、禁用词表；default.md 和类型文件的排版 | 必须遵循 |
| style.md 口头习惯 | 要表达这个意思时用这里的说法，不多用 |
| 讲事和解释（style.md、default.md 和类型文件都有） | 遇到这个场景时照这样写，材料不适合时换个写法 |
| default.md 和类型文件的结构 | 参考 |
| default.md 和类型文件的固定表达 | 有对应位置时照写 |

理由：

- 同一节里的规则性质相近：标点和禁用词能逐字判对错；口头习惯是换词；讲事和解释是某个场景下怎么讲。放进哪节就定了怎么用，learn 不用逐条定档，人读档案也不用先记几档的定义。
- 用法写在节标题下，不写在使用说明里：只拿到 style.md 路径的 agent（如复查的子代理）也能看到；用法改动时只改 archive-format.md，旧档案重跑 setup 换成新的。
- default.md 和类型文件也有讲事和解释一节：只在这个体裁成立、又要靠判断的写法（如代码放多少）放这里。放进排版会变成必须遵循，却没法逐字判对错。
- 讲事和解释不写成参考：这一节的规则多数来自作者的手改，写成参考，任何偏离都能算按材料取舍，复查查不出来。写成遇到场景时照做，复查时场景出现而没照做的会列出来；材料不适合时仍可以换写法。
- 例子和范文的语气、句子写法要学，内容不搬：措辞也划给本次材料的话，例子就传不了语气。例子原文一字不改，里面的标点和错字以标点和排版为准。
- 口头习惯不写成参考，也不写成照做：这一节决定稿子像不像作者，写成参考，agent 会按自己的习惯写；写成照做，口头禅每处都用，读起来像模仿。所以写成要表达这个意思时用这个说法，是换词，不是加词。
- 「适用」写规则用在哪里，所有规则都可以写，只在这些地方用。位置写具体，不写次数，理由同下文「规则交给模型判断，不用数字阈值」；也不写「少用」，模型对这类模糊词的理解和人不一致。
- 要避开的写法反着写成目标写法，免得把它带进上下文。例外是禁用词表：作者删掉过、模型默认会写的词和短语，反着写压不住，逐条列出并带改法，复查时在全文里逐条搜索。

代价：讲事和解释的规则多了以后，稿子可能变僵；每条靠「适用」和例子限定场景。

### 候选和校准

- candidates.md 收写稿 skill 追加的手改和原话，以及入档时作者说先不定的条目，每条带来源。手改用和规则相同的 `<改前>` `<改后>` 标签，升级时原样搬过去。只出现一次的手改也列给作者，问是一贯写法还是只针对那一篇；同一种改法出现在两篇不同稿子，或作者明说是一贯写法时，列给作者确认后升级成规则。
- 规则被推翻时先缩窄，作者确认不再要时才删。
- 校准：作者要求时，用一篇不在范文里的亲笔稿列出素材，让子代理按 index.md 的使用说明重写，对比差异，归为档案没写到、写了没照做、规则和原文相反三类，经作者确认后改档案。只在作者要求时做，因为要开子代理整篇重写。

代价：档案不在仓库里，个人风格不进 evals；要测时在用例里放一份样例档案。每个要用档案的项目都要运行一次 setup。写稿时读范文，占用的上下文更多。

## 规则交给模型判断，不用数字阈值

写作类 skill 的规则写目的和判断依据，由模型按具体稿件裁定，不设字数、句数、行数、次数这类阈值。

- 规则写清要达到的效果和判断时看什么。例如分段写成“一段讲完一层意思，一段在手机上读着太长时，在意思转折处分开”，不写“每段不超过 N 句”。
- 需要反复确认时，靠多轮检查，不靠数字门槛。
- 数字只在它本身是事实时出现：外部接口的限制、材料里的数据、用户指定的篇幅。风格档案每个类型收一两篇范文，这是档案的容量，写稿时不拿它衡量稿件。

理由：句子长短差别很大，行数取决于字号、屏宽和发布工具，写稿时算不出来。写成数字后，模型会去满足数字，而不是数字背后的目的；按“每段 1–3 句”拆段时，模型数着句子换行，不看拆开后每段的意思是否完整。

判断会随模型和稿件浮动，一致性靠规则写清目的和 evals 用例校准。
